## 1. 设计目标

命令系统服务于**一个**场景：**用手机 QQ 遥控 DSH 的会话**。因此它的设计约束与聊天机器人完全不同：

- 屏幕小 → 输出必须分页、命令必须短（两字中文）；
- 盲操作 → 任何时候都必须能一条命令问出"我现在在操作谁"；
- 误发代价高 → 宁多一步确认，不可静默把消息发给意料之外的会话；
- 不需要在 WebUI 出现 → **不接 `ctx.commands` 原生注册表**（D11）。

## 2. 两个正交的概念（一切设计的根）

| 概念 | 含义 | 持久化 | 变更方式 |
|---|---|---|---|
| **工作区作用域**（workspace scope） | 当前会话列表的可见范围，也是 `/新建` 的归属 | ✅ 与目标一起持久化 | `/切换 <序号\|路径>` |
| **控制目标**（control target） | 当前接管的具体 DSH 会话；`null` = **未选中态** | ✅ | `/会话 <序号\|标题>`、`/新建`、目标失效时自动清空 |

**一对持久化记录**（同一存储单元，避免二者不一致）：

```
{ openid, workspaceId: string | null, targetSessionId: string | null, updatedAt }
```

> 为什么要一起存：`/切换` 会**只改作用域并清空目标**（D19），若两者分开存储，重启后可能出现"作用域为空但目标非空"这种无法自洽的状态。

## 4. 入站消息状态机（优先级顺序）

每个 openid 独立维护自身状态。**优先级自上而下**，先命中先返回：

```
收到 C2C 消息 (openid, raw)
│
├─ 1. 有 pending 审批？              → 交给审批决策解析，return
├─ 2. 有 pending 提问？              → 交给提问作答解析，return
│
├─ 3. raw 不以 '/' 开头（非斜杠消息）
│     ├─ 取消该 openid 的分页状态（D22）
│     ├─ 控制目标 == null（未选中态）
│     │     ├─ `allow_create_session=false` → 回执「请先 /会话 选会话」，**不转发**，return  ← D19/D27
│     │     ─ 否则 **自动新建会话（D36）**：有工作区作用域落在该作用域，否则落在默认工作区
│     │           `$DSH_HOME/workspace/default`（惰性 mkdir -p + 注册）
│     │           → 登记 sessionId→openid 映射 → 回执「已在工作区「X」新建会话」（只报工作区名）
│     │           → **本条消息继续作为该会话的首个 prompt**
│     └─ 控制目标 != null
│           ├─ 该 agent 当前有未结束 turn → **steer 注入当前 turn**（D7）
│           └─ 否则 → followup（开启新 turn）
│
└─ 4. 斜杠命令
      ├─ 分页状态活跃 且 命令 ∈ {下一页, 上一页} → 翻当前列表，return   ← D22
      ├─ 分页状态活跃 且 命令 ∉ {下一页, 上一页}
      │     └─ **退出分页**，继续按下面的命令分发处理（不吞掉该命令）      ← D22
      ─ 命令分发
            ├─ /会话 /切换 /新建 /状态 /帮助 → 在未选中态下也可用
            ├─ /模型 /思考 /权限 /停止 /下一页 /上一页（无分页时）
            │     └─ 未选中态：回执「请先 /会话 选会话」，**不报错不中断**（D27）
            └─ 未知命令 → 回执未知命令提示，**不转发给 agent**（对齐旧项目）
```

**关于"不设分页超时"**：用户明确选择的是"跨页连续编号 + 无关命令自动退出分页"，**未选**"加超时失效"版本 → 分页状态**不设 TTL**，只由事件（非斜杠消息、无关斜杠命令）退出（D22）。

## 5. 分页规则

- **列表命令**（`/会话`、`/切换` 无参）共用分页能力，但**分页状态必须记住自己属于哪个列表**，否则 `/下一页` 无法判断该翻哪一个：
  ```
  { openid, listKind: 'sessions' | 'workspaces', workspaceId, page }
  ```
- **页码与编号**：跨页连续编号。第 1 页显示 `1..10`，第 2 页显示 `11..20`，因此 `/会话 13` 在第 2 页之后依然有效（D22）。
- **翻页命令是专属的**：`/下一页` `/上一页` 只在分页状态活跃时有意义；无分页时按普通命令处理（回执提示）。
- **翻页提示的出现条件（D38，2026-09-15 用户拍板）**：`/下一页` `/上一页` **不在 `/帮助` 中列出**（帮助页只列 9 个主命令）；列表 footer 的「翻页：…」提示**仅在列表条目超过 1 页（即 >10 条）时展示**，单页列表只保留「选择：…」提示。`/会话` 与 `/切换` 两个列表**统一**遵守此规则（修复前 `/会话` 单页也提示翻页、而 `/切换` 多页反而完全没有翻页提示）。
- **退出条件**：
  1. 非斜杠消息 → 退出分页，并按 §4 第 3 步继续处理该消息；
  2. 无关斜杠命令 → 退出分页，并**正常处理该命令**（不丢弃）；
  3. 到达列表边界 → 回执"已经是第 N 页/最后一页"，**保持在分页状态**。
- **无超时**（D22）。
- `/会话` 的列表项内容（D33 / **D46 改**）：**序号 + 会话标题 + 相对活跃时间**（如 `1. 修 bug 3小时`；**最新在前**）。标题来自 `ctx.sessionQuery.readTitleSnapshots`（live agent 的 `ctx.sessionTitle.get` 兜底）；无标题的**空白会话**显示「（新会话）」，其余无标题会话按 id 短形式显示。**不显示"当前目标"标记**（用户明确不需要）。时间拿不到就**整段省略**（D46）。

## 6. 会话寻址（三级优先级）

`/会话 <参数>` 的参数按下列顺序尝试解析（D23）：

1. **序号**：参数是纯数字 → 取当前分页列表中的第 N 项（跨页连续编号）；
2. **标题模糊匹配**：对当前工作区会话标题做包含匹配（大小写不敏感）→ 唯一命中则选中；命中多个 → 列出候选并请用户用序号重选（**不得静默取第一个**）；
3. **标题全文匹配**：与第 2 步同源，仅作为精确优先的补充。

> 寻址**不需要**用户输入完整 sessionId（手机输入体验差）；这是与旧项目（支持完整 id / 前缀）的有意差异。

**工作区寻址**（`/切换 <参数>`）同理：纯数字 → `/切换` 列表中的序号；否则按路径精确匹配（路径须与 `workspace.json` 中已注册的 `path` 规范化后一致），再退化为标题模糊匹配。

## 7. 关键行为的边界细则

### 7.1 `/新建`（D24 / D25 / D26）

| 场景 | 行为 |
|---|---|
| `/新建` 无参 | 在**当前工作区作用域**下新建；未选中态时用作用域（D27） |
| `/新建 <相对路径>` | 相对路径基准为 **`$HOME`**（不随会话 cwd 变） |
| `/新建 <路径>`，路径已注册为工作区 | 直接在该工作区下新建 |
| `/新建 <路径>`，路径未注册但目录存在 | 自动注册工作区 → 在该工作区下新建 |
| `/新建 <路径>`，目录不存在 | **`mkdir -p` 递归创建**，再注册工作区 → 新建 |
| `/新建 <路径>`，路径存在但是**文件** | **报错**（明确回执"该路径是文件，不是目录"），不创建会话 |
| 创建目录/注册工作区/创建会话任一失败 | **如实回执具体环节原因，绝不假成功**（`AGENTS.md` §3.3） |
| 二次确认 | **无**（用户明确不做二次确认） |
| 新建会话 id | `session-<uuid>`（与原生一致，`encodeSegment` 后成为会话目录名） |
| 新建会话标题 | **不给参数**，交由 DSH `sessionTitle` 自动生成 |
| 新建后控制目标 | **立即切为新会话**（D25） |
| 新建会话的模型/思考/权限 | 插件**不做任何初始化写入**，走 DSH 官方行为（D26） |

**参考事实**：`CreateAgentOptions.sessionId` 为**必填**且无原生 mint 助手（`dsh-agent/lib/types/index.d.ts:48-50`），故 id 由本插件生成；`sessionTitle.rename` 会 pin 显式标题并压制自动生成（`dsh-session-title/lib/types/index.d.ts:135`），本项目**不使用**它，故自动命名正常工作。

### 7.2 控制目标生命周期（D28 / D29 / D30）

| 事件 | 行为 |
|---|---|
| 选定会话（`/会话 <参数>`） | 设为控制目标并持久化 |
| `/新建` 成功 | 新会话立即成为控制目标并持久化 |
| `/切换 <工作区>` | **清空控制目标**（进入未选中态），持久化 |
| 插件启动 | 读取持久化记录；**有目标则自动恢复并 resume 该会话**；无记录则为未选中态（D28） |
| 目标已被 WebUI 归档 / 持久化不存在 | **自动清空为未选中态，并主动回执告知**（"原目标已被归档或不存在，请重新 /会话 选"）（D29） |
| 选定历史会话需 resume 且遇排他锁冲突 | ①**优先 `ctx.agents.get(id)` 复用 live agent**（WebUI 已加载时无需 resume，根本无冲突）；②真需 resume 时**立即如实回执**（E12-B 实测：锁由 live agent 的 write handle 持有，13ms 即 `SessionAlreadyOwnedError`，**内部盲重试无意义，已取消退避重试**）；③**如实回执**"该会话正被占用（可能是 WebUI 正在使用），请稍后重试或换会话"；④**绝不降级新建空会话**（D30） |

> ④ 是旧项目的实测教训：`agents.resume().catch(() => agents.create({sessionId}))` 会以同名新建空会话，**历史丢失且无日志**。本方案将其列为禁止行为。

### 7.3 忙闲与 steer（D7）

**判忙的权威依据已核实**（不再是待办）：

- 【源码明写】DSH 提供 `turnBoundary` 会话投影：`TurnBoundaryProjection` 的 `openTurnStartSeq` 字段注释为
  **"Seq of the open turn's `turn/start`, or null between turns"**
  （`dsh-agent/lib/types/types.d.ts:60-72`）。
- 【源码明写】该投影由 `@deepseek-ai/dsh-agent` 注册为**host-only 单元**（只声明在 `SessionProjectionStateMap`，
  不在客户端可见的 `SessionProjectionMap`）：`dsh-agent/lib/types/projection.d.ts:1-8`。
- 【源码明写】读取方式为 `ctx.sessionProjections.stateOf(session, 'turnBoundary')`
  （`dsh-session-projection/lib/types/index.d.ts:175`）。

**判定规则**：`turnBoundary.openTurnStartSeq !== null` ⇒ **忙**（有未结束 turn）⇒ 非斜杠消息走 `steer`；
为 `null` ⇒ 空闲 ⇒ 走 `followup`（`dsh-agent/lib/types/runtime-types.d.ts:192` 为 `followup`、`:200` 为 `steer`）。

> 备选实现：自行维护 `turn/start` ↔ `turn/end` 配对（napcat 的 `activeTurns` 做法，已在 0.1.5 上验证）。
> 本方案**优先用官方投影**，仅在投影不可用时才降级为自维护配对——不引入 `as any` 兜底。

### 7.5 `msg_seq` 槽位分配（风险 R9 · 由探针 E2 实测确认）

**背景【实测】**：QQ 单聊的被动回复以 `(msg_id, msg_seq)` 为唯一键。探针 E2 确认：**一段流式会占用一个 `msg_seq` 槽位**——两段流式分别用掉 `msg_seq=1`/`2` 后，同一 `msg_id` 的普通消息 `seq=1`/`2` 被拒 `40054005 消息被去重，请检查请求msgseq`。

**这是一个真实的一等约束**，因为它直接决定本项目"流式正文 + 审批卡片 + 提问卡片 + 命令回执"如何在同一条入站消息上共存。

**规则**：

1. 维护 **per-`msg_id` 的槽位分配器**：`{ msgId → Set<usedSeq> }`，每个出站消息必须取一个**未被占用**的 `msg_seq`，取用后登记；
2. **正文流式优先占格**（它是最长生命周期的占用者），随后审批卡片、提问卡片、命令回执依次取下一个空闲格；
3. 流式**全程复用同一个 `msg_seq`**（分片靠 `index` 递增），不得每片自增——自增会瞬间耗尽槽位（这也修正了 nyagent 的逐片自增写法）；
4. **不做"4 次上限"防御**（D9；E1 实测该上限当前未强制执行），但**槽位唯一性是硬约束**，必须防重；
5. 槽位表随 `msg_id` 生命周期回收（被动窗口 60 分钟）。

**验收要求**：契约测试必须断言——同一 `msg_id` 下，流式用过的 `msg_seq` 不会被后续审批/提问/回执复用；且流式分片的 `msg_seq` 恒定。

## 8.4 后续新增决策（D43，2026-09-15 用户拍板）

> 起因：真机测试时发现——agent 在正文还没推完时就立刻调用了触发审批的工具，
> QQ 侧正文被**截断到只剩一个「沙」字**。用户判定：这是真实问题。

根因（代码级，非推断）：交互卡片走 `index.ts` 的 `reply` → `QqStreamManager.sendSerialized`，
其第一步就是 `await endActive()`（**抢跑收流**）；而正文增量由 `turn-router` 的 per-openid
**异步链**处理（每个 delta 都 `await push`，可能含网络发送），**天然滞后于事件发射**。
抢跑收流时 `session.buffer` 只有第一个增量，之后 `push` 全因 `finished` 被丢弃；且 `turn-router`
的 `state.handle` 仍指向这条已结束的流，attempt `end` 帧到达时 `finish(full)` 因幂等直接返回
⇒ **整段正文永久丢失**。

| # | 维度 | 决策 |
|---|---|---|
| D43 | 普通消息与正文流共存 | **发任何普通消息（审批/提问卡片、命令回执、错误回执）之前，必须先等该 peer 的在途正文流处理完，再收流**。实现：`QqStreamManager.sendSerialized` 新增 `settleStream` 钩子（接线层接 `turn-router.drainPeer`）；`TurnRouter` 新增 `drainPeer(openid)`（只等该 peer，不阻塞其它 openid）。**禁止**任何路径"抢跑收流"。唯一例外：`turn-router` 自身的降级发送路径（它正在该链内部执行）显式传 `awaitStreamSettle: false`，否则会自等待死锁。等待失败**不得**阻断消息送达（记 `warn`，尽力而为） |

**为什么不是"让流一直开着"**：那会改变「普通消息 ⇒ 先收流」的既有不变式与 `activeSeq` 语义，
进而影响 `msg_seq` 槽位分配（R9/E2-2）；D43 只**增加一次等待**，不改流生命周期，风险最小。

   后挂载的服务此刻尚未注册，`ctx.get` 只返回**当时**的快照 ⇒ 旧实现
   `optionalService(ctx,'sessionController')` 恒 `undefined`。**必须改用
   `ctx.inject(['sessionController'], cb)` 动态注入**（或等价的「调用时惰性解析」）；**不能**写进静态
   `inject` 数组——该服务在 headless/base-only 装配里不存在，写进去会让插件永远等待、`apply` 不执行。
   ⚠️ **更正**：本条最初被归因成「跨 bundle 组被 `isolate` 隔离」，是**错的**——同一探针在
   `apply+2s` 用**普通 `ctx.get`** 就能拿到该服务（若有隔离边界则永远拿不到）。真实机制是**时序**。
   ⇒ **规矩**：任何**可选**服务都必须在**调用时**解析，或用 `ctx.inject` 等它就绪后再接线
   （既有先例：`src/tools/index.ts:200` 的 `ctx.inject(['tools'], …)`、
   `src/index.ts:175` 的 `ctx.inject(['settings'], …)`）。
2. **用户真实 profile 是 `web`**，其中 `@michengai/dsh-archive-manager` 用 `disabled: true` 摘掉官方

   ⇒ 只有装了这个插件，`blank`/`lastPromptAt` 才有值。**探针必须带上它**，否则读的是空的规范 domain，
   结论会失真（第一次跑探针就踩了这个）。
3. **`this` 绑定坑**：把 `optionalService(...)?.list` **裸取**出来会丢 `this` → 调用即抛 → 被控制层的
   降级分支静默吞掉（表现为「一切都对，就是没有时间」）。必须 `bind`。已由真机探针抓到，
   并在 `tests/contract/assembly.test.ts` 加了「依赖 `this` 的桩」回归用例（去掉 `bind` 即转红）。

> **方法论教训**：探针必须用**生产作用域**驱动。第一版探针在 boot 完成后用宿主 ctx 调 `wire()`，
> 对上述根因**给出假绿**——这正是 AGENTS §3.1「单测全绿 ≠ 装配可达」在探针层面的同类陷阱。

## 8.9 回合级归属（D49，2026-09-16 用户拍板）

> 起因（用户报告）：*"我刚才是在 webui 和你对话的，但是 qq 那边因为控制的是这个会话，
> 所以 qq 那边也能收到回复，同时有可能鉴权或者提问也走 qq。"*
>
> 调研：`docs/调研-受控会话的回合归属与回复路由-2026-09-16.md`（只读子代理 + Lead 复核）。

### 根因（复核过的三条）

1. **出站只按会话级映射**：`src/outbound/turn-router.ts` 的三个入口（帧 / 会话事件 / 串行化入队）
   全部只查 `openidOf(sessionId)`，**没有任何「这个 turn 由谁发起」判定** ⇒ 会话在受控映射里，
   WebUI 发起的回合正文照样发 QQ。
2. **卡片同理**：`src/inbound/interactions.ts` 两个 waterfall 都 `{prepend:true}`，claim 只看
   `controlledBy(sessionId)`（与 turn 无关），命中后**不 `next()`** ⇒ WebUI 转发器根本不执行。
3. **放大器（独立缺陷）**：`sessionOwner` 是**只写不删**的历史映射（写于自动新建与每条入站消息，
   全仓无 delete/clear）⇒ `/会话` 切走后旧会话仍常驻，其在 WebUI 的回合继续串台。
   D40 已把**卡片**判据换成 `findControlOwner`，但**正文出站没换**。

### 官方没有「回合来源」字段（只能桥接侧自记）

- `ApprovalRequestEvent = {agent, toolName, callId?, reason?, signal?}`（`dsh-user-approval/lib/types/types.d.ts:55-66`）、
  `AskUserQuestionRequestEvent = {questions, agent?, signal?}`（`dsh-user-questions/lib/types/types.d.ts:60-67`）——**都没有来源**；
- `SessionSummary` / `sessionListMetadata` 也不带来源；`lastPromptAt` 的谓词 `source.kind === 'user'`
  对 WebUI 与 QQ **完全同质**（`dsh-api-session-controller/lib/types/list.js:28-36`）；
- **可用判据**：`Message.id` 官方明写跨表示边界稳定（`dsh-llm/lib/types/message.d.ts:119-122`），
  且 `'user/message'` 会话事件的 data **就是**该 `UserMessage`（`dsh-session/lib/types/types.d.ts:281`）
  ⇒ 桥接投喂时自记 `Message.id`，用事件对拍即可判定回合归属。

### 决策

| # | 维度 | 决策 |
|---|---|---|
| D49 | 归属粒度与路由 | ① 把 D40 的「会话级受控」修订为**回合级归属**：出站与卡片都要求「该会话**当前回合由本桥接投喂**」；② WebUI 发起的回合，审批/提问卡片 **`next()` 委派回 WebUI**；③ QQ 侧对 WebUI 回合**完全不镜像、不标注**（避免噪音与误导）；④ 顺带修 `sessionOwner` 只写不删——出站归属改为**实时反查控制目标表** `findControlOwner` |
| 归属规则 | 最后一条**真人 prompt** 决定 | 新 turn 覆盖旧值；**QQ steer 进 WebUI 回合**时归属翻到 QQ（QQ 用户确实主动戳了该回合，回复给他才合理）。判定只认 `source.kind === 'user'` |

### 关键实测（真机装配测试抓到，否则会静默失效）

**每回合 DSH 还会注入一条 `source.kind === 'plugin'` 的 system-prompt 快照**
（`@deepseek-ai/dsh-system-prompt`，form=`snapshot`），它**同样是 `user/message`**。
若不排除，它会在我们自己的消息之后立刻把归属翻成「非 QQ」⇒ **QQ 自己的回合也不出站**（全链路静默）。
因此判定谓词与官方 `lastPromptAt` 对齐：**只认 `source.kind === 'user'`**。
（该陷阱由 `tests/contract/assembly.test.ts` 的真实装配用例抓出，见下。）

### 实现

- `src/index.ts`：`openidOf` 改为 `control.findControlOwner`（删掉只写不删的 `sessionOwner`）；
  新增回合归属表 + `session/event` 的 `user/message` 监听（仅 `source.kind === 'user'`）；
  把 `ownTurn` 显式接线给 **turn-router** 与 **interactions**；`QqBridgeWiring` 暴露 `isOwnTurn` 供装配断言。
- `src/dsh/control.ts`：`send()` 投喂时记下 `Message.id`（有界 256 条）；新增 `isOwnMessage(id)`。
- `src/outbound/turn-router.ts`、`src/inbound/interactions.ts`：新增**可选**依赖 `ownTurn`；
  未接线时保持旧行为（⇒ **既有测试零改动**），生产显式接线。

### 验收

- 契约测试 **+6**（全套 **331/331**）：router 2 条（`ownTurn=false` 时零出站、`true` 时照旧出站）、
  interactions 3 条（审批/提问在 `ownTurn=false` 时委派；`true` 时仍抢卡片）、
  assembly 1 条（**真实装配**：未投喂时 `false` → 桥接 `send()` 后 `true`，
  且实测 `user/message` 事件的 `Message.id` **确实等于**桥接记录的那条）。
- 既有测试**未改动一行**（可选依赖策略），仍全绿。

### 真机验收（2026-09-16，用户当面确认，【实测】）

**两个方向都验过**（同一受控会话）：

| **WebUI** 驱动本回合 | `ask_user_question` + 工作区外写文件被沙箱拒绝后升级的审批 | **两张卡片都只在 WebUI**，QQ 无卡片、未串台 ✓ |

**计划模式叠加验收（同日，用户确认）**：在计划模式下同样遵守该判据——

⇒ 计划模式与 D49 归属叠加时行为符合预期（该并发边界从「未覆盖」升为「已覆盖基本路径」，
但回合中途 steer 的并发仍见 C-R9）。

> ⚠️ **实现读法提醒（差点再次翻车）**：`dsh-api-session-controller` 给 `MessageSourceMap`

   但未真机验证该场景（真机验收只覆盖了「纯 WebUI 回合」）；
2. **其它裸 `{kind:'user'}` 生产者**（如 `dsh-plan-mode` 的 `/plan on` 也会发裸 source）会被判为
   「非 QQ 回合」⇒ 其输出不进 QQ；该清单未穷尽；
3. 归属表**不持久化**：进程重启后、QQ 尚未投喂前归属为「非 QQ」（保守不出站）。这与用户拍板一致，
   但「重启后 QQ 侧是否要恢复上下文中已有的回合」未讨论。

## 8.10 按请求维度设防：长正文不再被静默截断（D50，2026-09-16 真机缺陷修复）

**触发（用户报告）**：QQ 上收到的一条长回复被截断，且**无任何报错/告警**。实测复现：一条 **6118 码点**的
回复只送到 **4000 码点**，截断点与 `QqMarkdownAdapter` 里硬编码的 `QQ_MARKDOWN_MAX_CHARS = 4000`
**逐字吻合**（用生产 `dist/` 跑真机文本，输出恰好 4000 码点、结尾停在同一个字）。

**根因（三层叠加）**：
1. `toQqMarkdown()` 把**整段累积正文**按**码点**截到 4000；
2. `append` 模式每次只发**增量**（`formatted.slice(sentFormatted.length)`）⇒ `formatted` 一旦冻结在
   第 4000 码点，**增量恒为空**，后半段**永久发不出去**；
3. 失败判定基于 HTTP/业务码 ⇒ 全程 200，**既不回退也不告警**，`finish()` 只补一个空末片。

**平台真实约束（E3 真机实测 2026-09-16；用户口径：不采信腾讯文档，一切实测）**：

| 维度 | 实测结果 |
|---|---|
| 单次流式请求 `content_raw` | **∈ [20414, 20426) 字节 ≈20 KiB**，按 **UTF-8 字节**计（CJK 6781✅/6812❌；ASCII 20406✅/20437❌），失败码 `40054018` |
| 单条流的**累积总量** | **≥20000 字符（≈60 KB）无约束**，`remain_msg_len` 恒 0 |
| 单条**非流式** markdown | **≥32000 CJK 字符（96 KB）未触限**（真实上限未定界） |
| 主动流式（无 `msg_id`） | 不支持（`50015001`） |

**决策（用户拍板「甲：按请求维度设防 + 绝不静默」）**：

| 项 | 决策 |
|---|---|
| 适配层职责 | `toQqMarkdown()` **不再截断**，只做规范化（`#` 补空格 + 字符集净化）；新增 `splitByBytes(text, limitBytes)`：按 UTF-8 字节、码点安全、优先换行边界、`join('') === 原文` |
| 流式路径 | `pendingPayloads()` 把"尚未下发"部分切成每片 ≤ `QQ_STREAM_REQUEST_MAX_BYTES`（**8 KiB**，实测上限的 ≈2.5× 余量）的多片 `append`；末片仍承担 `input_state=10` |
| replace 模式 | 递进前缀（每片以上一片为前缀，规避 `40007`）；累积全文超单次上限后**余量改用 `append` 续发**（**【推断】未真机实测**；replace 非生产路径，生产恒 append，失败也只走回退） |
| 非流式路径（降级整发 / 失败回退 / 交互卡片 / 命令回执） | 一律按 `QQ_MESSAGE_MAX_BYTES`（**16 KiB**）**切条续发**，每条各占**独立 `msg_seq`**；任一条失败即停并如实返回失败码 |
| 硬截断 | **全部取消**。仅命令回执保留 `truncateReply`（本身带可见 `…`） |
| 空末片 | **保留**（【实测 E3-D】平台接受），且**恒用 `append`** 发出（replace 下空 payload 违反"必须是累积全文"语义） |

**真机缺陷红→绿**（同一输入、同一生产构建）：修复前送达 4000 码点（丢 2118）；修复后送达
**6118 码点、与原文逐字一致、丢弃 0**，末片 `input_state=10`。

**代价**：超长回复现在会**拆成多条 QQ 消息**（原先是被静默截断）；阈值取保守值而非平台上限。
